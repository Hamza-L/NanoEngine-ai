Vulkan backend

The biggest, oldest, most feature-complete backend. About 3,700 lines split across seven files. Runs on Windows only.

File layout

src/renderer/vulkan/
├── ne_renderer_vulkan.c          Public entry + frame loop      (1274 LOC)
├── ne_swapchain.h                  Swapchain vtable
├── ne_swapchain_vulkan_wsi.c       Standard WSI implementation    ( 440 LOC)
├── ne_swapchain_dxgi.c             DXGI + DirectComposition path  ( 777 LOC)
└── internal/                       Backend internals, split by concern
    ├── ne_vulkan_globals.h         NE_VK_MAX_FRAMES_IN_FLIGHT = 2
    ├── ne_vulkan_loader.h          Function-pointer table + loader
    ├── ne_vulkan_renderer.{c,h}    struct NERenderer + shared helpers
    ├── ne_vulkan_buffers.{c,h}     Buffers (static, dynamic) + image slots
    ├── ne_vulkan_images.{c,h}      Image creation (uses buffers pool)
    ├── ne_vulkan_pipelines.{c,h}   Deferred pipeline compilation
    └── ne_vulkan_shaders.{c,h}     SPIR-V + glslang runtime path

Dynamic loading — no link-time Vulkan

Traditional Vulkan apps link against vulkan-1.lib at build time. The engine takes a different approach: it declares VK_NO_PROTOTYPES and loads every function pointer at runtime.

// src/renderer/vulkan/internal/ne_vulkan_loader.h — ~70 function pointers
extern PFN_vkCreateInstance vkCreateInstance;
extern PFN_vkCreateDevice   vkCreateDevice;
extern PFN_vkAllocateMemory vkAllocateMemory;
// ... 60+ more ...

// Boot sequence
HMODULE lib = LoadLibraryA("vulkan-1.dll");
PFN_vkGetInstanceProcAddr vkGetInstanceProcAddr = GetProcAddress(lib, "vkGetInstanceProcAddr");
ne_vk_load_loader();              // resolves the "global" functions
ne_vk_load_instance_fns(instance); // resolves the "instance" functions
ne_vk_load_device_fns(device);     // resolves the "device" functions
Why bother? Two reasons: (1) the app runs even on machines without the Vulkan SDK installed — you don't need the import library at build time. (2) It lets the engine query the loader for extension-specific functions cleanly.

The renderer struct

// src/renderer/vulkan/internal/ne_vulkan_renderer.h
struct NERenderer {
    HMODULE  vulkan_lib;

    VkInstance       instance;
    VkPhysicalDevice phys;
    VkPhysicalDeviceMemoryProperties mem_props;
    VkDevice         device;
    VkQueue          queue;
    uint32_t         queue_family_index;

    // Three resource pools
    NEPool buffers;      // NEVulkanBufferSlot (also stores images via union)
    NEPool shaders;      // NEVulkanShaderSlot
    NEPool pipelines;    // NEVulkanPipelineSlot

    // Shared staging buffer for static-buffer uploads
    VkBuffer        staging_buffer;
    VkDeviceMemory  staging_memory;
    void           *staging_mapped;

    // Command buffer dedicated to transfers
    VkCommandPool   transfer_cmd_pool;
    VkCommandBuffer transfer_cmd;
    VkFence         transfer_fence;

    NEShaderOptimization shader_optimization;

    struct NERenderSurface *surfaces;   // intrusive linked list
};

The surface struct

// src/renderer/vulkan/ne_renderer_vulkan.c
struct NERenderSurface {
    NERenderer *renderer;
    NEWindow   *window;

    VkSurfaceKHR   surface;
    NESwapchain   *swapchain;          // vtable-driven — WSI or DXGI
    VkRenderPass   render_pass;

    VkCommandPool   cmd_pool;
    VkCommandBuffer cmds[2];               // one per flight frame
    VkSemaphore     sem_image_available[2];
    VkFence         fences_in_flight[2];
    uint32_t        frame_index;           // wraps 0, 1

    bool  vsync;
    float clear_color[4];

    NERenderPass pass;                     // embedded, returned by begin_frame
    NEPresentBackend present_backend;
};
💡 The pass is embedded, not heap-allocated

NERenderPass is a small token holding the current command buffer + pipeline layout + render pass. Because it lives inside the surface struct, begin_frame can just return its address — no allocation per frame.

Boot sequence — ne_renderer_create

All synchronous — ne_renderer_create returns a fully-usable renderer.

The frame loop

This is the meat of the Vulkan backend. About 200 lines total, but every line matters.

NERenderPass *ne_renderer_begin_frame(NERenderer *r, NERenderSurface *s) {
    uint32_t frame = s->frame_index % 2;

    // 1. Wait for the GPU to finish frame N-2 (the one that used cmds[frame])
    vkWaitForFences(r->device, 1, &s->fences_in_flight[frame], VK_TRUE, UINT64_MAX);

    // 2. Rebuild swapchain if the window resized (or first frame)
    if (s->swapchain->needs_recreate) {
        s->swapchain->ops->recreate(s->swapchain, s->vsync);
    }

    // 3. Ask the swapchain for the next image
    if (!s->swapchain->ops->acquire(s->swapchain, s->sem_image_available[frame])) {
        return NULL;   // window minimized / swapchain out of date — skip
    }

    // 4. WSI needs per-image fence tracking to avoid re-using an image the GPU still owns
    /* (skipped for DXGI, which uses fence-based sync internally) */

    // 5. Reset fence + command buffer, then record
    vkResetFences        (r->device, 1, &s->fences_in_flight[frame]);
    vkResetCommandBuffer (s->cmds[frame], 0);
    vkBeginCommandBuffer (s->cmds[frame], &begin_info);

    // 6. Begin the render pass — LOAD_OP_CLEAR wipes the screen to clear_color
    vkCmdBeginRenderPass(s->cmds[frame], &rpi, VK_SUBPASS_CONTENTS_INLINE);

    // 7. Set the viewport with Y flipped (matches OpenGL vertex convention)
    VkViewport vp = {
        .x = 0, .y = (float)s->swapchain->extent.height,
        .width  =  (float)s->swapchain->extent.width,
        .height = -(float)s->swapchain->extent.height,
    };
    vkCmdSetViewport(s->cmds[frame], 0, 1, &vp);

    // 8. Fill in the pass token and hand it back
    s->pass.cmd = s->cmds[frame];
    return &s->pass;
}

And the end:

void ne_renderer_end_frame(NERenderer *r, NERenderSurface *s) {
    uint32_t frame = s->frame_index % 2;

    vkCmdEndRenderPass  (s->cmds[frame]);
    vkEndCommandBuffer  (s->cmds[frame]);

    // Submit — the GPU waits for image_available, signals render_finished
    VkPipelineStageFlags wait_stage = VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT;
    VkSubmitInfo si = {
        .waitSemaphoreCount   = 1, .pWaitSemaphores   = &s->sem_image_available[frame],
        .pWaitDstStageMask    = &wait_stage,
        .commandBufferCount   = 1, .pCommandBuffers   = &s->cmds[frame],
        .signalSemaphoreCount = 1, .pSignalSemaphores = &render_finished,
    };
    vkQueueSubmit(r->queue, 1, &si, s->fences_in_flight[frame]);

    // Present — the OS composites the new image on the next vsync
    s->swapchain->ops->present(s->swapchain, r->queue, render_finished);

    s->frame_index = (s->frame_index + 1) % 2;
}
💡 The Y-flip trick

OpenGL uses Y-up, Vulkan uses Y-down. Rather than change every vertex shader, the engine flips the viewport: y = height, height = -height. This is a Vulkan 1.1+ feature (VK_KHR_maintenance1, now core) and it lets you write "Vulkan OR OpenGL" shaders that Just Work.

Sync primitives at a glance

The CPU stays exactly one frame ahead. The fence throttles it whenever the GPU falls behind.

Notable quirks

  • The singleton is enforced. A second ne_renderer_create call returns null — checked via a global g_renderer_singleton.
  • Images share the buffers pool. NEVulkanBufferSlot has a union: it's either a buffer allocation or an image allocation. Saves code duplication but is a bit of an oddity.
  • No GPU memory allocator. Every buffer/image calls vkAllocateMemory directly. Fine for the demo; won't scale to real scenes.
  • The DXGI swapchain skips the semaphore chain. It waits with a plain fence and vkDeviceWaitIdle. Works but stalls the GPU.
  • Compute pipelines are stubs — ne_compute_pipeline_create allocates a slot but never compiles. ne_render_pass_begin_compute logs a warning and returns null.
  • glslang linked as static libs. The Win32 build fetches glslang 16.5.0 as a release zip and links five .lib files. Big binary; fast startup.
How this could be better
  • Add a GPU memory allocator. Either integrate VMA or roll a simple slab allocator. Would unlock any real workload.
  • Support Vulkan on Linux and macOS (via MoltenVK). The backend already isolates platform code to vkCreateWin32SurfaceKHR — swapping that for vkCreateXcbSurfaceKHR / vkCreateMetalSurfaceEXT is a small change.
  • Pipeline cache. VkPipelineCache persisted to disk would cut startup time on subsequent runs.
  • Dedicated transfer queue. The engine uses one queue for everything. A separate transfer queue would let uploads overlap with drawing.
  • Descriptor sets. Nothing besides push constants exists for uniform data. Real scenes need bind groups.
  • Compute path. The scaffolding is there — just needs the fill-in.

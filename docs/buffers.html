Buffers & memory

Getting your data into the graphics card's memory. There are two strategies, and picking the right one makes a huge difference.

Why memory is complicated

Your computer has two kinds of memory: system RAM (fast for the CPU, slow for the GPU) and video RAM (fast for the GPU, invisible to the CPU). Some data lives in one, some in the other.

Think of it like two buildings across the street from each other. The CPU works in Building A. The GPU works in Building B. Data in Building A is fast for the CPU to reach, slow for the GPU. And vice versa.

The engine gives you two strategies for handing data over. You pick with one flag when you create the buffer.

// From include/ne_renderer_buffer.h
typedef struct NEBufferDesc {
    uint32_t size;
    NEBufferUsage usage;      // VERTEX, INDEX, or UNIFORM
    const void *initial_data; // optional
    bool dynamic;             // ← the important choice
} NEBufferDesc;

Strategy 1 — Static buffer (dynamic = false)

For data that never changes: the vertices of a mesh, a level's geometry, a texture. Upload once, then the GPU reads it at full speed forever.

The staging buffer is the "airlock" between the two memory spaces.
💡 The staging buffer is shared

The engine keeps one staging buffer on the renderer, reused for every static upload. It's mapped once, written many times, and never freed until the renderer is destroyed.

staging_buffer, staging_memory, staging_mapped — see ne_vulkan_renderer.h.

Strategy 2 — Dynamic buffer (dynamic = true)

For data that changes every frame: rotating vertices, animated particles, per-frame uniforms. You want to avoid the staging-buffer copy — that's a lot of work to redo every 16ms.

Two persistently-mapped copies. CPU writes one, GPU reads the other. No staging, no copy command.
// Inside the frame callback
static void on_frame_update(NEFrameContext *ctx, NERenderPass *pass) {
    Vertex rotated[3] = { /* new positions */ };

    // Under the hood, this does a memcpy into copy[frame_index]
    ne_render_pass_update_buffer(pass, ctx->vertex_buffer,
                                 rotated, sizeof(rotated), 0);
}
A dynamic buffer isn't one buffer — it's an array of them, one per "in-flight" frame. When you update it, you're really writing to copies[frame_index]. Because of the fence in step 1 of the frame lifecycle, the engine knows the GPU is done reading copies[frame_index] before you touch it.

When to use which?

Use caseStaticDynamic
A mesh loaded from disk✅No — waste of memory
Level geometry, terrain✅No
Rotating triangle vertices (this demo)No — one CPU→GPU copy per frame✅
Per-frame uniforms (small)NoOK — but push constants are better
Text vertex buffer that changes when the string doesNo✅

Push constants — the third option for small data

For tiny per-draw data (a transform matrix, a color, a flag), there's an even faster path: push constants. The data is embedded directly in the command buffer — no separate buffer, no memory allocation.

float mvp[16] = { /* model-view-projection matrix */ };

// 64 bytes of matrix data, attached to the next draw call
ne_render_pass_set_uniform_data(pass, NE_SHADER_STAGE_VERTEX,
                                /* offset */ 0,
                                mvp, sizeof(mvp));

Under the hood on Vulkan, this becomes a vkCmdPushConstants call. The limit is 128 bytes total (guaranteed by all Vulkan hardware). Enough for one 4×4 matrix plus a bit of extra data.

⚠️ Push constants are a per-draw thing, not per-frame

They live in the command buffer, so their lifetime is the draw call that follows. If you set them, then don't draw, the data is thrown away. That's the point — they're cheap.

How the three backends handle this

The engine's public API is the same everywhere, but the underlying strategies differ because the graphics APIs differ.

Concept Vulkan Win Metal Mac WebGPU Web
Static upload path Shared staging buffer + vkCmdCopyBuffer No staging — unified memory, direct write Buffer created with mappedAtCreation, then unmapped
Dynamic buffer copies 2 (matches frames-in-flight) 2 3
Storage mode DEVICE_LOCAL for static; HOST_VISIBLE for dynamic MTLStorageModeShared — everything is shared WebGPU picks — internally staged if needed
Push constants (128B) Native — vkCmdPushConstants Native — setVertexBytes: (up to 4 KB!) ❌ Not implemented — WebGPU has no equivalent
⚠️ Push constants don't work on WebGPU yet

WebGPU deliberately doesn't have a push-constant equivalent. On the WebGPU backend, ne_render_pass_set_uniform_data currently just logs a warning and does nothing. The demo doesn't use it, so it works — but any real app would need to emulate this with a uniform buffer + bind group.

Under the hood: the buffer slot struct

// From src/renderer/vulkan/internal/ne_vulkan_buffers.h
typedef struct NEVulkanBufferSlot {
    bool occupied;
    bool dynamic;

    union {
        struct {
            // Static: one buffer, one allocation
            VkBuffer buffer;
            VkDeviceMemory memory;
        };
        struct {
            // Dynamic: N buffers, N allocations, N mapped pointers
            VkBuffer dyn_buffers[NE_VK_MAX_FRAMES_IN_FLIGHT];
            VkDeviceMemory dyn_memories[NE_VK_MAX_FRAMES_IN_FLIGHT];
            void *dyn_mapped[NE_VK_MAX_FRAMES_IN_FLIGHT];
        };
    };
    // ... plus an image path via a second union arm ...
} NEVulkanBufferSlot;
How this could be better

The memory story is where the engine has the most room to grow up:

  • No GPU memory allocator. Every buffer and image calls vkAllocateMemory on its own. On real hardware, drivers cap you at ~4096 allocations total — this doesn't scale past a few thousand resources. A real allocator (like VMA) would grab a few big slabs and sub-allocate.
  • Only one staging buffer. All static uploads serialize through it — a big mesh upload will make you wait. A rotating pool of staging buffers, or a growable one, would fix that.
  • Destruction is immediate. When you destroy a buffer, the engine issues vkDeviceWaitIdle up front to be safe. That stalls the whole GPU. Deferred destruction (wait until GPU has moved past this frame) would remove that stall.
  • No descriptor sets. All uniform data goes through push constants — 128 bytes max. Anything larger (textures, big uniform structs) needs descriptor sets, which the engine doesn't have yet.

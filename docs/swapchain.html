The swapchain

The pool of images the display cycles through — and how the engine hides the fact that Windows has two completely different ways to do this.

What's a swapchain?

To draw smoothly, you need at least two images: one the display is showing right now, and one you're drawing the next frame into. When the next frame is ready, they swap. That's a swapchain.

Usually 2 or 3 images. The driver picks — the engine just asks "which one can I draw into?"

The interesting design choice: two backends

On Windows, there are actually two ways to present a swapchain image to the screen. Both work, but they trade off differently.

Vulkan WSI (standard)

The "textbook" path. vkCreateSwapchainKHR. Portable. What every Vulkan tutorial shows. Simple.

DXGI + DirectComposition

Windows' own compositor. More setup, but you get per-pixel window transparency — real alpha, real drop shadows, real acrylic looks.

The engine supports both, chosen at surface creation:

// From include/ne_renderer.h
typedef enum NEPresentBackend {
    NE_PRESENT_BACKEND_DEFAULT     = 0,
    NE_PRESENT_BACKEND_VULKAN_WSI  = 0,
    NE_PRESENT_BACKEND_DXGI        = 1,
} NEPresentBackend;

// Choose per surface
NERenderSurface *surface = ne_renderer_create_surface(renderer, window,
    &(NERenderSurfaceDesc){
        .vsync = true,
        .present_backend = NE_PRESENT_BACKEND_DXGI,
    });

How the engine hides the difference

This is a genuinely tidy piece of design. Both backends are stored behind a single interface — a struct of function pointers:

// From src/renderer/vulkan/ne_swapchain.h
typedef struct NESwapchainOps {
    void (*destroy) (NESwapchain *);
    bool (*recreate)(NESwapchain *, bool vsync);
    bool (*acquire) (NESwapchain *, VkSemaphore image_available);
    bool (*present) (NESwapchain *, VkQueue, VkSemaphore render_finished);
} NESwapchainOps;

struct NESwapchain {
    NESwapchainOps *ops;    // ← the vtable

    VkFormat format;
    VkExtent2D extent;
    uint32_t image_count;
    VkImage *images;
    VkImageView *image_views;
    // ...
};

The Vulkan backend's frame loop uses surface->swapchain->ops->acquire(...) and ops->present(...) — it doesn't know or care which of the two implementations is behind those pointers.

A tiny vtable makes two very different systems interchangeable.
This pattern — a struct of function pointers you swap between implementations — is C's version of "polymorphism" or "interfaces". It's how FILE * in the C standard library works: one type, different underlying drivers.

The DXGI path in more detail

DXGI is Microsoft's own graphics infrastructure — the same thing DirectX uses. The tricky bit is that we're rendering with Vulkan but presenting with DXGI. How?

DXGI creates the images, Vulkan borrows them via a shared-handle extension, then DirectComposition puts them on screen with real alpha.

The magic ingredient is VK_KHR_external_memory_win32, a Vulkan extension that lets you import a Windows-native memory handle as a VkImage. Once imported, Vulkan draws into it exactly like any other image.

DirectComposition then takes those images and composes them with the rest of the desktop, honoring alpha per-pixel. That's what gives the demo window its transparent-with-shadow look.

Present-mode choices (Vulkan WSI path)

Vulkan lets you pick how images are handed to the display. The engine's WSI path picks based on the vsync flag:

ModeBehaviorVsync?Tearing?
FIFO Queue images, present on vsync. Always available. ✅ ❌
MAILBOX Present the newest image on vsync, drop older ones. Low latency. ✅ ❌
IMMEDIATE Present ASAP, ignore vsync. ❌ ✅

Preference: vsync = true → FIFO. vsync = false → prefer MAILBOX → IMMEDIATE → fall back to FIFO.

Resize handling

When the window changes size, the swapchain images no longer match. The engine handles this lazily:

  1. OS fires a resize event (WM_SIZE).
  2. The window handler sets swapchain->needs_recreate = true. Cheap.
  3. On the next begin_frame, the engine sees the flag and calls ops->recreate(new_size).
  4. The old images are destroyed, new ones created at the right size, and drawing continues.

This deferred approach avoids doing expensive work during the resize event itself, which on Windows blocks the main loop.

How industry engines present frames

The "which present path" question is genuinely contentious. NanoEngine offering both WSI and DXGI-with-DirectComposition on the same backend is unusually flexible:

  • Most Vulkan games on Windows — use standard WSI. Simple, portable, works with any Vulkan-capable window. No transparency support.
  • Microsoft's own PIX + DirectX games — DXGI flip-model swapchains, sometimes with DirectComposition for overlays. Windows-only but tightly integrated with the OS compositor (variable refresh rate, HDR handshake, tearing control).
  • Vulkan Vulkan-DX interop (like NanoEngine's DXGI path) — historically rare. Popularized by Doom Eternal (which shipped a Vulkan+DXGI path for HDR) and more recently by tooling engines like Blender and Krita that want transparent Vulkan windows on Windows.
  • Present-mode preference — AAA games default to MAILBOX (low latency vsync) when available, fallback FIFO. Competitive shooters offer IMMEDIATE (tearing OK) for lowest input lag. NanoEngine follows the same preference order.

The swapchain-as-vtable design also mirrors what real engines do: bgfx's "renderer interface" abstracts D3D11/D3D12/Vulkan/Metal presentation behind function tables, exactly like NESwapchainOps.

How this could be better
  • The DXGI path skips the standard semaphore chain. It uses a fence + vkDeviceWaitIdle internally, which stalls the GPU. A native DXGI/Vulkan interop fence (via VK_KHR_external_semaphore_win32) would remove the stall.
  • Present-mode isn't exposed through the public API. You get "vsync on/off" — no way to explicitly ask for MAILBOX for low latency. Adding a NEPresentMode enum would fix this.
  • WebGPU is hardcoded to FIFO. The public vsync field isn't plumbed through on the web backend.
  • HDR is not supported anywhere. All backends hardcode BGRA8Unorm (or equivalent). No RGB10A2, no scRGB, no color-space negotiation.

A frame, step by step

Every frame the engine draws goes through the same eight-step dance. Let's follow one from start to finish.

The two players

Rendering is fundamentally a conversation between two things:

The CPU (your code)

Writes a to-do list — "clear the screen, use this pipeline, draw these vertices, show the result". Doesn't do the actual drawing.

The GPU (the graphics card)

Reads that to-do list later and performs each command. Very fast at drawing many things in parallel.

The CPU is like a chef writing a recipe. The GPU is like an army of kitchen assistants who follow the recipe at high speed. The chef doesn't cook — they only write.

The eight steps

The CPU (left) and GPU (right) work in parallel. The CPU is usually one frame ahead.

The most important idea: frames in flight

The CPU and GPU work at the same time. While the GPU draws frame 5, the CPU is already writing the to-do list for frame 6. This keeps both busy.

But we need to make sure the CPU doesn't get too far ahead — otherwise it would overwrite data the GPU is still reading. The engine solves this by allowing exactly two frames in flight at a time:

At any moment, the CPU is preparing frame N+1 while the GPU is drawing frame N, and the display is still showing frame N−1.

The safety net: fences and semaphores

Two kinds of "wait for something" primitives keep everyone in sync:

PrimitiveWho waits for whom?What for?
Fence CPU waits for GPU "Is the GPU done with frame N−2 yet? If not, I'll block."
Semaphore GPU waits for GPU "Don't start drawing until the swapchain image is actually ready."

Each surface keeps two of each — one per flight frame:

// From ne_renderer_vulkan.c
VkCommandBuffer cmds[2];                  // per flight frame
VkSemaphore     sem_image_available[2];   // per flight frame
VkFence         fences_in_flight[2];      // per flight frame
uint32_t        frame_index;              // wraps 0, 1, 0, 1, ...
A fence is a mailbox: the GPU drops a letter in when it finishes. The CPU checks the mailbox. A semaphore is a red light between two GPU steps: the acquire step signals green, the draw step waits for green.

What happens when the window resizes?

The swapchain images are sized to match the window. If you resize the window, they no longer fit, and the driver tells us so on the next present. The engine responds like this:

Resize is lazy. The engine defers the expensive rebuild to the top of the next frame.

On Windows there's an extra twist: while the user is actively dragging the edge, the OS blocks the main loop. The engine works around this by hooking WM_SIZE and calling the render callback inline — so the window keeps updating during the drag.

How industry engines drive frames

Two frames in flight is the default across the whole industry. Some notable specifics:

  • Unreal Engine 5 — 2 frames on desktop, 3 on mobile (to hide higher latency variance). Uses a dedicated "RHI thread" that records commands in parallel with the game thread.
  • Unity (URP/HDRP) — 2 frames. Uses a "render graph" that plans the whole frame's passes ahead of time, then submits.
  • id Tech 7 (Doom Eternal) — 2 frames, but with an async compute queue running lighting/particles in parallel. Same fence pattern NanoEngine uses, applied twice.
  • DXR / RTX games — sometimes 3 to hide ray-tracing latency spikes.

NanoEngine's swimlane (CPU records N+1 while GPU draws N) is the fundamental pattern. What the big engines add on top: multithreaded command recording, async compute, and predictive frame pacing to avoid missed vsyncs.

How this could be better

Two things about the current frame loop could improve:

  • Only one queue. The engine uses one GPU queue for everything (graphics + present). Real-world engines split into a "graphics" queue, a "transfer" queue for uploads, and a "compute" queue for GPU jobs — so uploads can happen in parallel with drawing.
  • Only two frames in flight. Two is safe but a bit conservative. Three would let the CPU work further ahead when the GPU is the bottleneck. It's a config number (NE_VK_MAX_FRAMES_IN_FLIGHT) — trivially bumpable.

The four layers

Everything in the engine lives in one of four layers. Each talks only to the layer directly below it.

Each layer knows about the one directly below. Nothing reaches across.

The ownership chain

Objects in the engine follow a strict parent-child relationship. If you destroy a parent, everything below it goes with it — like pulling a tablecloth.

The app owns windows. The renderer (a singleton) owns surfaces and three pools of GPU resources.

Create top-down, destroy bottom-up

// Create — top to bottom
app      = ne_app_create();
window   = ne_window_create(app, ...);
renderer = ne_renderer_create(&desc);
surface  = ne_renderer_create_surface(renderer, window, &sdesc);

// ... use them ...

// Destroy — reverse order
ne_renderer_destroy_surface(renderer, surface);
ne_renderer_destroy(renderer);
ne_window_destroy(window);
ne_app_destroy(app);
⚠️ Only one renderer at a time

The renderer is a singleton — the engine enforces this. Trying to create a second one while the first is alive will fail. This simplifies internal state (there's only ever one connection to the graphics card).

Layer 1 — Platform

The platform layer owns the connection to the operating system. There's one implementation per OS:

PlatformFileNative objects
Windows src/platform/win32/window_win32.c HWND, WM_* messages, DWM compositor
macOS src/platform/macos/window_macos.m NSApplication, NSWindow, NSView, CADisplayLink
Web src/platform/web/window_web.c HTML canvas, DOM events, requestAnimationFrame

All three implement the same public interface (include/ne_window.h) — ne_window_create, ne_window_destroy, ne_app_run, etc. Your code doesn't change when moving between them.

Think of this like USB. Your keyboard has one connector; laptops from three companies each accept it. The layer above doesn't care which brand of laptop it's plugged into.

Layer 2 — Renderer

The renderer is the "big object" in the engine. It owns:

  • The connection to the graphics card (Vulkan instance / Metal device / WebGPU device)
  • A list of surfaces — one per window it's drawing into
  • Three pools of GPU resources: buffers, shaders, pipelines
  • A shared "staging buffer" for uploading data (Vulkan only)

Just like the platform layer, there's one implementation per graphics API:

BackendDirectoryRoughly
Vulkansrc/renderer/vulkan/1274 LOC entry + 6 internal files
Metalsrc/renderer/metal/1180 LOC, one Objective-C file
WebGPUsrc/renderer/wgpu/1175 LOC, one C file

Layer 3 — Surface

A surface is the marriage between a renderer and a window. It's not really a separate "layer" as much as a bridge — but conceptually it sits between them. One surface per window; the renderer keeps them in a linked list.

What a surface holds:

  • The GPU's link to the window (Vulkan VkSurfaceKHR, Metal CAMetalLayer, WebGPU WGPUSurface)
  • The swapchain — the pool of images the display cycles through
  • Per-frame synchronization primitives (fences, semaphores)
  • Command buffers — the "to-do lists" the CPU writes and hands to the GPU
  • The clear color and vsync setting
A window is just a rectangle on screen. A surface is what makes that rectangle drawable from the GPU's point of view. On Windows, the surface says "here's an HWND, please draw into it".

Layer 4 — Frame dispatch

The thinnest layer. It's just a callback the engine invokes whenever a frame is due. The whole implementation is about 20 lines:

void ne_render_frame(void *user) {
    NEFrameContext *ctx = (NEFrameContext *)user;

    NERenderPass *pass = ne_renderer_begin_frame(ctx->renderer, ctx->surface);
    if (!pass) return;                          // window minimized, skip

    if (ctx->on_update) ctx->on_update(ctx, pass);

    ne_render_pass_set_pipeline    (pass, ctx->pipeline);
    ne_render_pass_set_vertex_buffer(pass, 0, ctx->vertex_buffer);
    ne_render_pass_draw            (pass, 0, ctx->vertex_count);

    ne_renderer_end_frame(ctx->renderer, ctx->surface);
}

This function is registered on the window. The platform layer calls it whenever a frame should happen:

  • Windows — every iteration of the main loop (pull model)
  • macOS — when CADisplayLink fires on vsync (push model)
  • Web — when requestAnimationFrame fires (push model)
How industry engines organize this

Most production engines use one of two shapes — NanoEngine is closest to the first but simplified:

  • Unreal, Unity, Godot — a big scene graph. You add "actors" or "nodes" to the world; the engine walks the tree each frame, culls what's off-screen, sorts by material, and issues draws for you. Very high-level, no manual draw calls.
  • bgfx, sokol_gfx, WebGPU-native samples — a command-recorder API like NanoEngine's, but the frame callback is more open-ended: you call set_pipeline / bind / draw as many times as you want. NanoEngine's NEFrameContext currently hard-codes a single draw, which is a stepping stone toward the same shape.

The four-layer split (App → Window → Renderer → Surface) mirrors what GLFW+bgfx or SDL+sokol_gfx look like — a common "small engine" pattern.

How this could be better

The frame dispatch is hard-coded to draw exactly one pipeline with one vertex buffer. That's fine for the demo, but real scenes have many draw calls with different pipelines, buffers, and textures.

A future version could let the user provide a list of draws in the context — or replace the callback signature with something more flexible like:

void on_frame(NERenderPass *pass, void *user);   // user does all the draws

That's actually what most engines end up with. The current shape is a stepping stone.

Shaders & pipelines

A shader is a tiny program that runs on the graphics card. A pipeline bundles two shaders plus the rules for turning vertices into pixels.

What's a shader?

Shaders are small programs written in a special C-like language. There are two kinds you'll use in this engine:

Vertex shader

Runs once per vertex. Given the vertex's raw data (position, color, etc.), computes where on the screen it should appear.

Fragment shader

Runs once per pixel (kind of). Computes the color of each pixel inside the triangle.

Here's the demo's vertex shader — 8 lines of GLSL:

// shaders/glsl/basic.vert
#version 450
layout(location = 0) in vec2 in_position;
layout(location = 1) in vec4 in_color;
layout(location = 0) out vec4 frag_color;

void main() {
    gl_Position = vec4(in_position, 0.0, 1.0);
    frag_color  = in_color;
}

And the fragment shader — even shorter:

// shaders/glsl/basic.frag
#version 450
layout(location = 0) in  vec4 frag_color;
layout(location = 0) out vec4 out_color;

void main() {
    out_color = frag_color;
}
The vertex shader says "put this vertex at this screen position". The fragment shader says "make this pixel this color". Both are called many times — a triangle covering 100 pixels calls the fragment shader 100 times, in parallel.

Two ways to load a shader

Both paths end up in the same place. The difference is who compiles the GLSL and when.

Pre-compiled path — ne_shader_create

size_t vert_size;
void *vert_spv = ne_file_read("build/shaders/basic.vert.spv", &vert_size);

NEShaderHandle vs = ne_shader_create(renderer, &(NEShaderDesc){
    .stage = NE_SHADER_STAGE_VERTEX,
    .bytecode = vert_spv,
    .bytecode_size = vert_size,
    .entry_point = "main",
});

Runtime path — ne_shader_create_from_source

const char *vert_glsl = /* raw GLSL text — read from disk or embedded */;

NEShaderHandle vs = ne_shader_create_from_source(renderer, &(NEShaderSourceDesc){
    .stage = NE_SHADER_STAGE_VERTEX,
    .source = vert_glsl,
    .source_size = strlen(vert_glsl),
    .entry_point = "main",
});

Under the hood, this calls glslang_shader_create → preprocess → parse → link → SPIRV_generate, then feeds the result through the pre-compiled path.

What's a pipeline?

A pipeline is a recipe for drawing. It bundles:

  • A vertex shader and a fragment shader
  • The layout of vertex data — "position is 8 bytes at offset 0, color is 16 bytes at offset 8"
  • What kind of primitives — triangles, lines, points
  • Blend state — how new pixels combine with what's already there
  • Depth/stencil settings (not used in the demo)

Once you build a pipeline, you can bind it during a frame and issue many draw calls against it — the recipe stays valid until you swap it out.

NEPipelineHandle pipeline = ne_pipeline_create(renderer, &(NEPipelineDesc){
    .vertex_shader   = vs,
    .fragment_shader = fs,
    .topology        = NE_TOPOLOGY_TRIANGLE_LIST,

    .vertex_bindings = &(NEVertexBinding){
        .stride = sizeof(Vertex),   // 24 bytes per vertex
        .attributes = (NEVertexAttribute[]){
            { .location = 0, .format = NE_FORMAT_R32G32_FLOAT,  .offset = 0 },
            { .location = 1, .format = NE_FORMAT_R32G32B32A32_FLOAT, .offset = 8 },
        },
        .attribute_count = 2,
    },
    .vertex_binding_count = 1,
});

The neat trick: deferred compilation

Compiling a pipeline is expensive — often several milliseconds. And to compile it, the graphics API needs to know the render pass format (what pixel format the output image uses, whether there's depth, etc.).

Problem: when you call ne_pipeline_create at startup, you might not have a surface yet. Or the surface might get resized and change format.

Solution: don't compile immediately. Store the recipe. Compile on first use.

Deferred compilation trades a slightly complex first frame for a much simpler API.
Think of it like a recipe you write down but don't cook until someone actually orders it. When the customer arrives, you know exactly what pan they want, so you can pick the right one — but the writing was done up front.

Fixed pipeline state in this engine

To keep the API small, the engine hard-codes a lot of pipeline state. If you need something different, you'd need to expand NEPipelineDesc.

How industry engines handle shaders & pipelines

Pipeline compilation stalls are one of the most notorious PC gaming problems. What the big engines do:

  • Unreal 5 — a PSO (pipeline state object) cache: on your first playthrough it compiles and streams the compiled blobs to disk. Later runs load pre-baked pipelines. Games ship with a "PSO precache" step for this reason.
  • Unity URP — "shader variant collections" — you pre-declare every pipeline combination you'll use and Unity compiles them ahead of time. Trades memory for smooth frames.
  • Modern Vulkan (1.3+) — graphics pipeline libraries: compile shaders once, mix and match them into full pipelines cheaply. Removes the "recompile everything if blend state changes" cost.
  • DirectX 12 with Agility SDK — supports "state objects" that separate common state from draw-specific state. Same idea as pipeline libraries.

Shader languages in industry:

  • Unreal writes HLSL, cross-compiles to SPIR-V/MSL/DXIL via its own translator.
  • Godot 4 writes GLSL, transpiles via glslang (same lib NanoEngine uses) + SPIRV-Cross for MSL/HLSL output.
  • Modern engines (2024+) increasingly adopt Slang — one HLSL-like language that compiles to every target.

NanoEngine's deferred-compile model is actually similar to what Unreal does with PSO caching, minus the disk persistence. The direction is right; the polish isn't there yet.

How this could be better
  • Cross-compile shaders. Right now you write GLSL for Vulkan, WGSL for the web, and MSL (or nothing) for Metal — three separate copies of every shader. A single source language (Slang, or SPIRV-Cross-compiled GLSL) would collapse this.
  • Compute pipelines are stubs on all three backends. The API declares them, but they log "not yet implemented" and return null.
  • Pipeline cache. A compiled pipeline is fully deterministic from its inputs. Storing compiled pipelines to disk (Vulkan supports this natively via VkPipelineCache) would cut startup time on later runs.
  • Pipeline libraries / dynamic state. Modern Vulkan lets you swap fragments of pipeline state (blend, topology) without a full recompile. Would remove the ~1ms hitch on any state permutation.

Handles & pools

Instead of returning raw pointers, the engine hands you tiny integer "tickets". Here's why, and how the tickets work.

The problem with raw pointers

If ne_buffer_create() returned a void *, you'd have to worry about:

  • What if I use it after it's been destroyed? (Crash.)
  • What if I check if (buf != NULL) — does that mean it's valid? (Only if nothing else freed it.)
  • Where in memory does it live? (Wherever malloc felt like putting it.)

Handles fix all three problems.

What a handle looks like

// From include/ne_renderer_buffer.h
typedef struct NEBufferHandle {
    uint32_t id;
} NEBufferHandle;

Just a 32-bit number. id == 0 is the null / invalid handle. id == 1 means "the resource at pool slot 0".

handle.id = slot_index + 1. That way id = 0 unambiguously means "invalid".

Why this is nicer than raw pointers

Validation is one compare

if (handle.id == 0) — that's the entire "is this valid?" check.

Dangling references caught

If you destroy a resource and then use the old handle, the engine looks at the slot, sees occupied = false, and warns instead of crashing.

Memory is contiguous

All slots live in one flat array. Cache-friendly, no fragmentation, easy to grow.

Small & cheap to pass

4 bytes. Fits in a register. Copies are free. No refcounting.

The pool underneath

Every kind of resource has its own pool. Every pool is a flat array of fixed-size slots. Every slot starts with one byte: bool occupied. The pool doesn't know or care what's in the rest of the slot.

// From src/ne_alloc.c — the essential shape (simplified)
typedef struct NEPool {
    uint8_t  *slots;      // flat array of slot_size bytes each
    size_t    slot_size;
    uint32_t  count;      // how many slots exist right now
    uint32_t  hint;       // scan starts here
} NEPool;

// Every slot type looks like this:
typedef struct NEVulkanBufferSlot {
    bool     occupied;    // MUST be first byte
    // ... type-specific fields ...
    VkBuffer buffer;
    VkDeviceMemory memory;
} NEVulkanBufferSlot;

Allocating a slot

Slot allocation is a linear scan. Fast when the pool isn't full.

Freeing a slot

Just flip occupied = false. If the freed slot is before the hint, rewind the hint so the next allocation finds it quickly. That's it.

Growing the pool

Starts at 16 slots. When full, doubles: 16 → 32 → 64 → … The old realloced array grows in place if possible; otherwise memory is copied.

🎯 Same pattern id Software used in Quake

The "flat array of slots with a scan-from-hint allocator" is a very old, very well-tested pattern. It's simple, fast for small-to-medium counts, and has zero fragmentation within a pool. The trade-off is that it's not thread-safe — but neither is the rest of the engine.

The three pools

The renderer holds three pools, one per resource kind:

// From src/renderer/vulkan/internal/ne_vulkan_renderer.h
struct NERenderer {
    // ...
    NEPool buffers;    // NEVulkanBufferSlot × N   (also stores images)
    NEPool shaders;    // NEVulkanShaderSlot × N
    NEPool pipelines;  // NEVulkanPipelineSlot × N
    // ...
};

Each pool stores a different slot type, but they all share the same underlying NEPool machinery. Handles from different pools are distinct types (NEBufferHandle vs NEShaderHandle) so the type system stops you from mixing them up.

🐛 Odd corner: images share the buffers pool

Vulkan images live in the same pool as buffers, using a union in the slot struct. This works but is a bit of an inconsistency. Also, NEImageHandle is a raw uint64_t instead of the struct { uint32_t id; } shape used by every other handle. See Rough edges.

How this could be better

The handle system works but is one small step away from being much sturdier:

  • Generational handles. Right now, if you destroy a buffer and quickly create a new one, the new buffer might live in the exact same slot. If you still had the old handle, it'd point at the new buffer without you noticing. A "generation counter" in the high bits of the handle (say, top 8 bits = generation, bottom 24 = slot) would catch this — every destroy bumps the generation, so old handles fail cleanly.
  • Unify the image handle. NEImageHandle should be struct { uint32_t id; } like the others.
  • Split images into their own pool. Buffers and images have very different lifetimes and sizes; sharing a pool via union costs memory when one type dominates.
  • Thread safety. No mutex on the pool right now. Fine for a single-threaded engine; would need locks (or per-thread pools) for multithreaded resource creation.
